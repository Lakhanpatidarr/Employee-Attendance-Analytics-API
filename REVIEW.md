# REVIEW.md

Review of the starter `app/main.py` (helpers and the four provided endpoints). Examples marked **(run)** were executed
against the starter's own helper functions; the rest follow directly from the code. All items are fixed in the
submitted `app/main.py`, which replaces the starter rather than patching it, because the helpers were wrong in ways that
spread into every endpoint.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Grace test is done on whole **minutes** (`int(seconds/60) > 10`), not seconds. A punch-in 10:00 to 10:59 after shift start is never late. R2 says strictly more than 10:00. | Shift 09:30, punch-in 09:40:01: starter returns 0, contract wants 10. **(run)** | Work in seconds: late if `delta > 600`, then `delta // 60` (`late_minutes_for`). |
| 2 | `compute_late_minutes` | Shift start is built with `punch_in.replace(hour=..)` in whatever time zone the datetime happens to carry, not IST. With UTC-aware or UTC-naive values the comparison is against 09:30 UTC. | Same instant 04:45:59Z (10:15:59 IST): starter returns 0, wanted 45. **(run)** | Anchor shift start as an IST instant for the attendance date (`at_ist`), compare instants. |
| 3 | `compute_late_minutes` | Overnight shifts ignored: shift start is always on the punch-in's own calendar day. | Shift 22:00-06:00, punch-in 05:00 IST: starter 0, correct 420 (it belongs to the previous day's shift, R1+R2). **(run)** | `attendance_date` assigns the record date per R1; lateness is measured from the shift start on that date. |
| 4 | `compute_work_hours` | Python `round()` on a float: not half-up (R4). Ties such as 0.015 round down. | 54 s of work: starter 0.01, correct 0.02; 554 mismatches in 1..40000 s. **(run)** This also corrupts R5 near 4.50. | `Decimal(seconds)/3600` quantized with `ROUND_HALF_UP`. |
| 5 | `compute_overtime` | No 30-minute minimum (R3): any positive minute counts. | Punch-out 18:35, shift end 18:30: starter 5, contract 0. **(run)** | Overtime is 0 unless the floor-minutes are at least 30. |
| 6 | `compute_overtime` | Shift end is always on the record date; overnight shifts end the next day. | 22:00-06:00, out 06:40 next day: starter 1480, correct 40. **(run)** | Add one day to the shift end when `shift_end <= shift_start`. |
| 7 | `compute_overtime` | Subtracts an aware IST datetime from `punch_out`; with PyMongo's default (naive) datetimes this raises. Latent 500 for the punch-out endpoint. | `TypeError: can't subtract offset-naive and offset-aware datetimes`. **(run)** | Client uses `tz_aware=True`; every datetime is aware UTC; helper compares instants. |
| 8 | module top (`MongoClient(...)`) | Client is not `tz_aware`, so every datetime read back is naive. | Stored instants lose their zone; item 7. | `MongoClient(..., tz_aware=True, tzinfo=UTC)`. |
| 9 | whole app | No indexes are created anywhere. Nothing enforces uniqueness (items 14, 21) and every filter and sort is a collection scan. | `db.employees.index_information()` shows only `_id_`; slow list at 100k records. | Seven indexes created idempotently in the lifespan hook, two of them unique. |
| 10 | `health` | Always returns 200 without touching MongoDB. Contract: 200 only if MongoDB answers, else 503. | Stop MongoDB, call `/health`: still 200. | Pings MongoDB; returns 503 on any failure. |
| 11 | `EmployeeIn` | No validation: emp_code format `EMP` + 4-6 digits, e-mail, `HH:MM` shift times, `shift_start != shift_end`, real `joined_on` date, length limits. | `{"emp_code":"x","shift_start":"99:99","joined_on":"hello"}` returns 201. | Pydantic patterns and a model validator; invalid input gives 422. |
| 12 | `PunchInIn.status` | Free `str`: `ABSENT`, `LEAVE` or `"banana"` is accepted at punch-in. Only PRESENT, WFH, ON_DUTY are allowed. | `{"status":"LEAVE","emp_code":..}` creates a LEAVE record with a punch time. | `Literal["PRESENT","WFH","ON_DUTY"]`. |
| 13 | `PunchInIn.punched_at` | Plain `Optional[int]`: accepts seconds-sized values, negatives, bools and numeric strings (lax coercion); huge values reach `fromtimestamp` and raise. | `punched_at: 1783312500` (seconds) is accepted; `10**20` gives `OSError`, a 500. **(run)** | Strict int in `[1e11, 4102444800000]`; everything else is 422. |
| 14 | `create_employee` | Check-then-insert race: concurrent creates of one `emp_code` all pass `find_one`; no unique index to stop them. | 10 parallel POSTs: several 201s and duplicate documents. | Unique index on `emp_code`; `insert_one` and catch `DuplicateKeyError` for 409. |
| 15 | `create_employee` | `created_at = datetime.now()`: naive **local** time. PyMongo stores a naive value as UTC, so the instant is wrong by the server's UTC offset. The response also returns an ISO string instead of epoch ms. | On an IST server `created_at` is 5.5 h in the future. | UTC datetime with ms precision; API returns epoch milliseconds. |
| 16 | `list_employees` | `skip = page * page_size` (should be `(page-1) * page_size`): page 1 skips the first page. | Seed 5 employees, `page=1&page_size=20` returns nothing (skip = 20). | `(page - 1) * page_size`. |
| 17 | `list_employees` | `total = count_documents({})` ignores the department filter (R10). | `?department=HR` reports the total of the whole company. | `count_documents` with the same filter. |
| 18 | `list_employees` | No sort: order is natural order, so pages are unstable; contract sorts by `emp_code`. No `page`/`page_size` bounds: `page=-1` gives a negative skip (ValueError, 500); `page_size=0` means "no limit" in PyMongo and returns everything. | `?page=-1` returns 500; `?page_size=1000` is allowed (max 100). | `.sort("emp_code")` (index-backed); `Query(ge=1)` and `Query(ge=1, le=100)`; `created_at` converted to ms. |
| 19 | `punch_in` | Unknown employee: `emp["shift_start"]` on `None` raises `TypeError`, a 500. Contract: 404. | Punch in for `EMP0000`. | Explicit 404 before use. |
| 20 | `punch_in` | `datetime.fromtimestamp(ms/1000)` is naive **local** time: the stored instant is shifted by the server's offset, the date is not the IST date (R1), milliseconds are kept (R1 truncates to seconds), and `if body.punched_at` treats 0 as "now". | 00:10 IST on 7 Jul becomes `2026-07-06` on a UTC server. **(run)** | `ms_to_dt` gives aware UTC truncated to seconds; `attendance_date` converts to IST and applies the overnight rule. |
| 21 | `punch_in` | Check-then-insert race again on `(emp_code, date)`: two simultaneous requests both pass `find_one` and both insert. Contract: exactly one 201, the rest 409. | 16 parallel punch-ins: several 201s, duplicate rows, later lookups ambiguous. | Unique `(emp_code, date)` index; `DuplicateKeyError` becomes 409. No read-before-write. |
| 22 | `punch_in` response | Returns `id` (the ObjectId as a string), which the contract forbids, and raw datetimes (ISO strings) for `punch_in`/`punch_out` instead of epoch ms. | Response has `"id": "66a..."`. | `serialize_record` builds the exact contract shape; no `_id`/`id`. |
| 23 | `list_attendance` | Loads **every matching document** into memory, sorts in Python, then slices; `total = len(docs)`. At 100k records this is slow and memory-heavy. | `/attendance` with no filter on the 100k dataset. | Server-side `sort`/`skip`/`limit`, `count_documents`, backed by `(date desc, emp_code)` and `(status, date, emp_code)` indexes. |
| 24 | `list_attendance` | Sorted by `date` only; contract is `date` desc, then `emp_code` asc. Ties come back in arbitrary order, so pagination can repeat or skip rows. | Two employees on the same date appear in different orders across pages. | Sort `[("date", -1), ("emp_code", 1)]`. |
| 25 | `list_attendance` | No validation: `date_from > date_to` should be 422; bad dates and unknown `status` values are accepted; `page`/`page_size` unchecked (`page=0` slices `docs[-20:0]`, silently empty). | `?date_from=2026-07-31&date_to=2026-07-01` returns 200. | Date, `Literal` status and bounded page types; explicit range check. |
| 26 | `list_attendance` | Returns `id` and raw datetimes; legacy documents without `half_day`/`history` come back without them. | Legacy sample (#9 in DATA_MODEL) lacks `half_day` and `history` in the response. | `serialize_record` defaults missing fields (`half_day` false, `history` [], counters 0) and converts instants to ms. |
| 27 | whole app | Starter has no `half_day` computation or helper, and the `punch_out`, `PATCH`, analytics and explain endpoints are TODO. Not a defect of the code, but required by the contract. | n/a | Implemented in `app/main.py` (R5 uses the **rounded** hours). |

## Looked at and judged fine (not defects)

- `load_dotenv()` is called with the default `override=False`, so real environment variables already win over `.env`, as the contract requires.
- `HTTPException(409, "...")` and `HTTPException(...)` bodies produce FastAPI's default `{"detail": ...}`, which is what the contract specifies.
- `doc.pop("_id", None)` after `insert_one` in `create_employee` is necessary (PyMongo adds `_id` to the dict) and correct, apart from the `created_at` issue in #15.
- The `shift_start`/`shift_end` defaults (`09:30`/`18:30`) match the contract; `body.model_dump()` cannot smuggle a client-supplied `created_at` because the model has no such field.
- Endpoints are plain `def`, so FastAPI runs them in its thread pool and the synchronous PyMongo client does not block the event loop. Concurrency is a data-layer problem here (#14, #21), not an event-loop one.
- `datetime.fromisoformat(date_str)` in `compute_overtime` is fine for `YYYY-MM-DD` input; the defects in that function are in what it does with the result (#5-#7).
